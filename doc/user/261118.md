# 2026-11-18 작업 일지

## 한 줄 요약
**카카오 로그인**을 붙였습니다. 둘러보기는 누구나 할 수 있고, 모임 만들기와 참여는 카카오 로그인을 해야 합니다. 참여 기록은 브라우저 쿠키 대신 **회원 ID**로 남깁니다.

---

## 1. 무엇이 바뀌었나

| 화면 / 기능 | 바뀐 점 |
|---|---|
| 상단바 | 로그인 전에는 "로그인", 로그인 후에는 프로필 사진, 닉네임, "로그아웃"이 보입니다 |
| 로그인 화면 (`/login`) | 노란 "카카오로 시작하기" 버튼이 있습니다. 키가 설정되지 않았으면 안내 문구가 대신 나옵니다 |
| 모임 만들기 | 로그인하지 않았으면 로그인 화면으로 이동합니다. 로그인을 마치면 만들기 화면으로 돌아옵니다 |
| 모임 상세 | 로그인 전에는 "카카오 로그인하고 참여하기" 버튼이 보이고, 로그인을 마치면 같은 모임 화면으로 돌아옵니다 |
| 참여 기록 | 게스트 쿠키(`NADEURI_GUEST`)를 없애고 회원 ID로 기록합니다. 쿠키를 지우거나 다른 기기를 써도 같은 사람으로 인식합니다 |

## 2. 사용한 기술

| 기술 | 역할 |
|---|---|
| Spring Security | 어떤 주소에 로그인이 필요한지 정하고, CSRF 공격을 막습니다 |
| Spring Security OAuth2 Client | 카카오 로그인 과정(인가 코드 → 토큰 → 사용자 정보)을 대신 처리합니다 |
| 카카오 로그인 API | `kauth.kakao.com`(로그인, 토큰), `kapi.kakao.com/v2/user/me`(닉네임, 프로필 사진) |

**OAuth2를 쉽게 말하면**: 우리 서비스가 비밀번호를 받지 않고, 카카오가 "이 사람 맞아요"라고 확인해 주는 방식입니다. 사용자가 카카오 화면에서 동의하면 카카오가 우리 서버로 돌려보내 주고(리다이렉트 URI), 우리 서버가 카카오에 닉네임과 사진을 물어봅니다.

**CSRF를 쉽게 말하면**: 다른 사이트가 몰래 우리 사이트로 "참여하기" 요청을 보내는 공격입니다. 그래서 폼마다 숨은 토큰을 넣어서 확인합니다. Thymeleaf의 `th:action`이 이 토큰을 자동으로 넣어 줍니다.

## 4. 결정한 것과 이유

| 결정 | 이유 |
|---|---|
| 둘러보기는 로그인 없이 허용 | 처음 온 사람이 바로 모임을 구경할 수 있어야 해서 |
| 카카오 키가 없어도 앱이 뜨도록 함 | 키 설정 전에도 개발을 계속할 수 있게. 이때는 로그인 화면에 안내만 나옵니다 |
| 카카오 연결 설정을 yml이 아니라 코드에 둠 | yml에 넣으면 키가 비었을 때 앱이 아예 안 떠서, 키가 있을 때만 켜지도록 코드로 처리 |

| `/gatherings/{id}/sign-in` 주소 추가 | 로그인 후 "보던 모임 화면"으로 돌아오게 하려고. 로그인이 끝나면 Spring Security가 이 주소로 돌려보내고, 여기서 다시 상세 화면으로 보냅니다 |

## 5. 테스트
테스트는 **15개 모두 통과**했어요. 기존 5개에 10개를 더했습니다.
- 로그인 없이 홈, 모임 상세, 지도 API를 볼 수 있음
- 로그인하지 않고 모임 만들기나 참여를 누르면 로그인 화면으로 이동
- CSRF 토큰이 없는 참여 요청은 거절(403)
- 로그인하면 참여되고, 상단바에 닉네임이 보이고, 버튼이 "참여 완료"로 바뀜
- 같은 카카오 회원이 두 번 로그인해도 회원은 한 명이고, 닉네임과 사진만 바뀜
- 카카오 응답 해석: 닉네임 동의가 없으면 "나들이 친구"를 쓰고, 회원번호가 없으면 거절
- 키가 있으면 로그인 버튼이 보이고, 누르면 카카오 로그인 화면으로 이동

화면 확인: H2 DB로 띄운 복사본(8899 포트)에서 상세 화면 버튼, 로그인 화면 이동, 상단바를 확인했어요. 실제 카카오 계정으로 로그인하는 건 아래 설정을 마친 뒤에 확인해야 합니다.

# 2부: 우리 사이트 로그인 (이메일 + 비밀번호)

## 한 줄 요약
카카오 계정이 없어도 **이메일과 비밀번호로 가입하고 로그인**할 수 있게 했습니다. 로그인 화면 하나에서 이메일 로그인과 카카오 로그인을 함께 고를 수 있습니다.

## 1. 무엇이 바뀌었나

| 화면 | 바뀐 점 |
|---|---|
| 로그인 (`/login`) | 이메일·비밀번호 입력칸, "이메일로 회원가입" 링크, 구분선 아래에 카카오 버튼이 있습니다 |
| 회원가입 (`/signup`) | 이메일, 닉네임, 비밀번호, 비밀번호 확인을 입력합니다. 잘못 입력한 칸 바로 아래에 이유를 보여 줍니다 |
| 가입 직후 | 로그인 화면으로 이동해서 "가입이 완료됐어요!"를 보여 주고, 이메일을 미리 채워 줍니다 |
| 로그인 직후 | 원래 가려던 화면(예: 보던 모임)으로 돌아갑니다 |
| 모임 상세 | 버튼 글자를 "카카오 로그인하고 참여하기"에서 **"로그인하고 참여하기"**로 바꿨습니다 |

## 2. 규칙
- **이메일**: 64자까지 쓸 수 있고, 대소문자를 구분하지 않습니다(`Foo@A.com`과 `foo@a.com`은 같은 계정). 같은 이메일로는 한 번만 가입할 수 있습니다.
- **비밀번호**: 8~64자이고, 영문과 숫자를 모두 넣어야 합니다.
- **닉네임**: 20자까지 쓸 수 있습니다.
- 로그인에 실패하면 "이메일 또는 비밀번호가 맞지 않아요"라고만 보여 줍니다. 어느 쪽이 틀렸는지 알려 주면 가입된 이메일을 알아내는 데 쓰일 수 있기 때문입니다.

## 3. 비밀번호는 어떻게 저장하나
- 비밀번호는 원래 글자 그대로 저장하지 않고 **BCrypt 해시**로 바꿔서 저장합니다. DB에는 `{bcrypt}$2a$10$...` 같은 값이 들어갑니다.
  - **해시를 쉽게 말하면**: 되돌릴 수 없는 암호문입니다. DB가 유출되어도 원래 비밀번호를 알기 어렵습니다. 로그인할 때는 입력한 비밀번호를 같은 방식으로 바꿔서 비교합니다.
- 앞에 붙은 `{bcrypt}` 표시 덕분에, 나중에 해시 방식을 바꿔도 예전 회원의 비밀번호를 그대로 확인할 수 있습니다.
- 로그인 검사가 끝나면 세션에서 해시값을 지웁니다.

## 4. 코드 변경
- `users` 테이블에 `password` 칸을 추가했습니다. 우리 사이트 회원만 값이 있고, 카카오 회원은 비어 있습니다. 이 칸은 앱을 다시 시작하면 자동으로 추가되므로 따로 할 일은 없습니다.
- 우리 사이트 회원은 `provider = local`, `provider_id = 이메일`로 저장합니다. 카카오 회원은 `provider = kakao`이고, 다음에 붙일 구글 회원은 `google`이 됩니다.
- 새 파일
  - `SignUpRequest`: 가입 폼
  - `LocalUserDetailsService`: 이메일로 회원을 찾음
  - `DuplicateEmailException`: 이미 가입된 이메일일 때
  - `signup.html`: 회원가입 화면
- **참여 처리 순서 변경**: "자리 있으면 +1"을 먼저 하고, 성공했을 때만 참여 기록을 저장하도록 바꿨습니다. 마감된 모임에 참여를 누르면 이제 참여 기록을 아예 건드리지 않습니다. 테스트용 H2 DB에서 동시 참여 테스트가 가끔 실패하던 문제도 이 변경으로 해결됐습니다. 정원 초과와 중복 참여를 막는 기능은 그대로입니다.

## 5. 테스트와 확인
- 테스트 **21개 모두 통과** (새로 6개 추가). 동시 참여 테스트는 8번 반복해서 돌려도 모두 통과했습니다.
  - 가입하면 비밀번호가 해시로 저장되고, 이메일은 소문자로 맞춰짐
  - 중복 이메일은 가입되지 않음
  - 가입 → 로그인 → 원래 가려던 화면으로 이동
  - 비밀번호가 틀리거나 없는 이메일이면 같은 오류를 보여 줌
  - 폼 검증 메시지가 보이고, 입력한 비밀번호는 화면에 다시 보내지 않음
- 브라우저 확인(8899 포트, H2 DB): 모임 상세에서 "로그인하고 참여하기" → 로그인 화면 → 회원가입 → 로그인 → 같은 모임으로 돌아옴 → 참여하기 → **2/6명, "참여 신청이 완료됐어요!"**까지 확인했습니다.

## 6. 해 주셔야 할 일
- IntelliJ에서 **앱을 다시 시작**해 주세요. DB 칸은 자동으로 추가됩니다.

## 7. 아직 없는 것 (다음 후보)
1. **구글 로그인**: 다음 작업
2. 같은 이메일로 이메일 가입과 소셜 가입을 따로 하면 지금은 다른 계정으로 취급됩니다. 계정을 연결하는 기능이 필요합니다.
3. 비밀번호 찾기: 메일 발송 기능이 필요합니다.
4. 로그인 시도 횟수 제한: 비밀번호를 계속 바꿔 가며 시도하는 공격을 막습니다.

# 3부: 지도에서 내 위치 바로 찾기 + 아이디로 회원가입

## 1. 지도에서 "내 위치로" 버튼

지도를 둘러보다 보면 내 위치를 다시 찾기 어려웠습니다. 그래서 아래처럼 바꿨습니다.

| 바뀐 점 | 설명 |
|---|---|
| **지도 안 "내 위치로" 버튼** | 지도 오른쪽 아래(범례 위)에 ⌖ 버튼이 생겼습니다. 누르면 다시 검색하지 않고 내 위치로 바로 이동합니다. 너무 멀리 축소돼 있으면 동네가 보이는 정도로 확대해 줍니다 |
| 버튼 색 | 지도 가운데가 내 위치면 **파랗게 채워지고**, 지도를 옮기면 흰색으로 돌아옵니다. 지금 내 위치를 보고 있는지 한눈에 알 수 있습니다 |
| 내 위치 표시 | 파란 점 주위로 **퍼져 나가는 물결**이 생겨서 모임 핀 사이에서도 잘 보입니다. 버튼을 누르면 점이 잠깐 커졌다 작아집니다 |
| 오차 범위 원 | 휴대폰이 알려 준 위치 오차(예: 반경 120m)를 옅은 파란 원으로 보여 줍니다. 오차가 2km를 넘으면 원이 화면을 덮어서 그리지 않습니다 |
| 위치를 못 찾을 때 | 지도 위에 이유를 보여 줍니다(예: "위치 권한이 꺼져 있어요. 주소창 왼쪽 아이콘을 눌러 위치를 허용해 주세요."). 전에는 말없이 여의도로 이동해서 내가 여의도에 있는 것처럼 보였습니다. 이제는 이미 찾은 내 위치가 있으면 그대로 둡니다 |
| 위쪽 "내 위치" 버튼 | 지금처럼 위치를 **새로 찾고 그 자리에서 모임을 다시 검색**합니다 |

- 위치는 더 정확한 방식(GPS 우선)으로 찾습니다. 30초 안에 찾은 위치는 다시 씁니다.
- 확인 방법: 8888 포트에서 가짜 위치(망원동)를 넣고, 지도를 멀리 옮기고 축소한 뒤 버튼을 눌렀습니다. 내 위치로 돌아오고, 확대 단계가 9에서 4로 바뀌고, 버튼이 파랗게 바뀌는 것을 확인했습니다. 권한 거부 안내 문구도 화면에 나오는 것을 확인했습니다.
- ⚠️ IntelliJ는 화면 파일(템플릿, CSS)을 `build` 폴더에 복사해서 씁니다. 그래서 수정한 뒤에는 **Build → Rebuild(Ctrl+F9)나 재시작**을 해야 8888 포트에 반영됩니다. 오늘 확인할 때도 8888 포트에 예전 파일이 섞여서 나왔습니다.

## 2. 이메일 대신 아이디로 회원가입

요청하신 대로 우리 사이트 가입·로그인을 **이메일에서 아이디로** 바꿨습니다.

- **아이디 규칙**: 영문으로 시작하고, 영문·숫자·밑줄(_)로 4~20자입니다. 대소문자는 구분하지 않습니다(`Walker`와 `walker`는 같은 아이디).
- 이미 사용 중인 아이디면 "이미 사용 중인 아이디예요"라고 알려 줍니다.
- 로그인 실패 문구는 "아이디 또는 비밀번호가 맞지 않아요"입니다.
- 오늘 잠깐 이메일로 가입한 계정이 있다면, 아이디 칸에 그 이메일을 넣으면 그대로 로그인됩니다.
- 비밀번호 찾기를 만들려면 나중에 이메일(또는 휴대폰)을 따로 등록받아야 합니다.

## 3. 테스트
**22개 모두 통과**했습니다. 아이디 관련 테스트를 바꾸고, "공백·@·한글·너무 짧은 아이디는 가입 안 됨" 테스트를 새로 넣었습니다.
브라우저 확인(8899 포트): 아이디로 회원가입 → 로그인 화면에 아이디 미리 채워짐 → 로그인 → 홈 화면, 상단에 "로그아웃" 표시까지 확인했습니다.

## 4. 지도 위치 점과 범례 표시 수정
- 내 위치의 퍼지는 효과와 정확도 원을 제거해 파란 점 하나만 보이게 했습니다.
- 지도 범례가 지도 타일에 가려지지 않도록 위에 표시하고, 화면 높이가 낮으면 지도 높이를 줄여 하단 범례와 버튼이 보이게 했습니다.
- 브라우저 화면 확인은 하지 않았습니다. 인라인 JavaScript 문법은 확인했습니다.

## 5. 지도 범례가 가려지는 문제 보완
- 범례를 지도 위에 겹쳐 놓지 않고 지도 제목 줄로 옮겨, 카카오 지도 레이어에 가려지지 않게 했습니다.
- 작은 화면에서도 두 안내 문구가 한 줄에 보이도록 스타일을 조정했습니다.

# 4부: 로그인 후 이상한 주소로 이동하던 문제

## 증상
로그인을 마치면 보던 화면이 아니라 `http://localhost:8888/.well-known/appspecific/com.chrome.devtools.json?continue`로 이동했습니다.

## 원인
- 이 주소는 우리 사이트의 페이지가 아닙니다. **Chrome 개발자 도구(F12)가 열려 있을 때 자동으로 보내는 요청**입니다("이 사이트의 소스 폴더를 개발자 도구에 연결해도 되나요?").
- 우리 보안 설정은 허용하지 않은 모든 주소를 "로그인 필요"로 막고, 막힌 주소를 **"로그인 후 돌아갈 곳"으로 기억**합니다. 그래서 Chrome의 요청이 기억됐고, 로그인 후 그 주소로 이동했습니다.

## 해결
1. `/.well-known/...` 주소는 로그인 없이 허용했습니다. 이제 그냥 "없는 페이지(404)"로 끝납니다.
2. "로그인 후 돌아갈 곳"은 **사람이 보는 화면 주소만** 기억하게 했습니다. `/.well-known`, `/api`, 오류 페이지, CSS 같은 파일, 화면 이동이 아닌 fetch 요청은 기억하지 않습니다.

## 확인
- 테스트 2개를 추가해서 **24개 모두 통과**했습니다.
  - 모임 만들기 화면 → (Chrome 자동 요청) → 로그인하면 **모임 만들기 화면으로** 돌아감
  - 돌아갈 곳이 없으면 로그인 후 **홈으로** 감
- 8888 포트에 반영하려면 IntelliJ에서 **앱을 재시작**해야 합니다(Java 코드가 바뀜).

# 5부: 8888 포트 최종 확인과 DB 정리

## 확인 결과 (앱 재시작 후)
| 항목 | 결과 |
|---|---|
| 아이디로 회원가입 → 로그인 | ✅ |
| 로그인 후 원래 보던 화면으로 이동 (Chrome 주소 버그) | ✅ |
| 지도 안 "내 위치로" 버튼 (실제 클릭) | ✅ 확대 9 → 4, 버튼이 파랗게 바뀜 |
| 모임 참여 | ✅ (DB 정리 후) "참여 신청이 완료됐어요!", 2/5명 |
| 모임 만들기 | ✅ (DB 정리 후) 만든 사람은 자동으로 "참여 완료" |

## DB 정리 (요청하셔서 직접 실행)
모임 만들기와 참여에서 500 오류가 났던 원인은 `participant` 테이블에 남아 있던 옛 `participant_key` 칸(값 필수)이었습니다. 아래 작업을 했습니다.
1. 옛 칸 `participant_key`와 옛 제약 `uk_participant_gathering_key`를 삭제했습니다.
2. 회원 정보가 없는 옛 게스트 참여 기록 1줄을 삭제했습니다.
3. 모든 모임의 인원 수를 실제 참여 기록에 맞게 다시 계산했습니다("저녁 5km 러닝" 2/8 → 1/8).

## 확인하면서 생긴 테스트 데이터 (필요 없으면 지우세요)
- 회원: 아이디 `claude_test01`, 닉네임 "테스트계정"
- 모임: "[테스트] 망원 저녁 산책" (8번)
- "연남동 골목 사진 산책" 모임의 참여 1건

→ 테스트 데이터는 요청에 따라 모두 지웠습니다(회원 `claude_test01`, 8번 모임, 참여 1건). 지운 뒤 모든 모임 인원을 다시 계산해서 지금은 모두 주최자 1명입니다. 브라우저 창의 테스트 로그인도 로그아웃했습니다.

## 6. 전체 화면 스타일과 안내 문구 정리
- 홈, 모임 등록, 모임 상세, 로그인, 회원가입 화면을 흰 배경·얇은 테두리·노란색 강조로 통일했습니다. 로그인과 회원가입은 참고 이미지처럼 중앙 카드 형태로 정리했습니다.
- 홈 화면의 검색 기준과 반경, 빈 결과·오류 상태를 구체적으로 표시합니다. 등록 화면에는 주최자를 포함한 정원과 한국 시간 기준을 안내합니다.
- 실행 중인 IntelliJ 앱은 `build`에서 CSS를 읽고 있어 최신 CSS를 실행 리소스에 복사했습니다.
- 브라우저에서 홈, 로그인, 회원가입 화면을 확인했습니다. 모임 등록은 로그인 화면으로 보호되어 있어 시각 확인하지 않았습니다.

# 6부: 날씨를 보며 모임 날짜·시간 고르기

## 무엇이 바뀌었나
모임 만들기의 **시작 시간**을 브라우저 기본 달력 대신 **우리만의 날씨 달력**으로 바꿨습니다.

1. **날짜 줄 (14일)**: 각 날짜에 요일(오늘·내일·모레), 날씨 아이콘, 최고/최저 기온, 강수확률이 보입니다. 토요일은 파란색, 일요일은 빨간색입니다. 예보가 없는 날은 "예보 없음"으로 보이지만 고를 수 있습니다. 14일보다 먼 날은 "더 먼 날짜 선택"으로 고릅니다.
2. **시간 줄 (0~23시)**: 시간마다 기온, 날씨 아이콘, 강수확률이 있고, 위에 **기온 그래프**가 있습니다. 이미 지난 시간은 고를 수 없습니다.
3. **분**: 00 / 15 / 30 / 45
4. **요약**: "11월 19일 (목) 오후 3:30 · ⛅ 구름많음 4° · 강수확률 20%". 비나 눈 예보가 있으면 주황색으로 안내합니다.

- 날씨 기준 위치는 **지도 중심 → 내 위치 → 고른 장소** 순서로 바뀝니다. 장소를 고르면 그 장소의 날씨로 다시 계산합니다.
- 서버로 보내는 값은 예전과 같은 형식(`2026-11-19T15:30`)이라 서버 쪽 처리는 바뀌지 않았습니다.

## 날씨는 언제까지 볼 수 있나 (직접 확인함)
기상청 단기예보를 오늘 20시 발표 기준으로 서울에 대해 직접 조회했습니다.
- **3일 뒤(11/21)까지: 1시간 단위**
- **4일 뒤(11/22): 3시간 단위** (사이 시간은 가장 가까운 예보를 씁니다)
- 그 이후는 단기예보에 없습니다.

발표 시각마다 범위가 조금씩 달라서, 화면 위에 "**예보는 11월 23일 오전 12시까지 있어요**"처럼 실제로 받은 범위를 그대로 보여 줍니다.
→ 더 먼 날(약 10일 뒤까지)도 보려면 기상청 **중기예보**를 추가로 활용신청해야 합니다. 중기예보는 오전/오후 단위로 나옵니다.

## 모임 만들기 지도의 "내 위치로" 버튼
장소 지도 오른쪽 아래에 ⌖ 버튼을 추가했습니다. 누르면 지도가 내 위치로 이동하고, 그다음 지도를 눌러 장소를 정하면 됩니다. 위치 권한이 없으면 안내 문구를 보여 줍니다.

## 새로 만든 것
- API: `GET /api/weather/forecast?lat=&lng=` (날짜별 요약 + 시간별 예보)
- `ForecastResponse` (날짜별로 묶고, 그날의 대표 날씨를 정함: 낮에 비·눈이 있으면 비·눈, 없으면 낮에 가장 많이 나온 하늘상태)
- `static/css/weather-picker.css` (이 화면 전용 스타일. app.css와 분리)

## 테스트와 확인
- 테스트 **28개 모두 통과** (날씨 묶기 테스트 4개 추가). 로그인 오류 문구가 다른 곳에서 바뀌어 테스트 1개를 그에 맞췄습니다.
- 브라우저 확인(8899 포트 임시 서버, 실제 기상청 데이터): 날짜·시간·분 선택 → 요약 → **모임 등록 → 상세 화면에 15:30과 같은 날씨가 표시됨**. 휴대폰 폭에서도 가로로 넘치지 않음.
- ⚠️ **모임 만들기 지도의 "내 위치로" 버튼은 아직 확인하지 못했습니다.** 카카오 지도가 8888 포트에서만 열리기 때문입니다. IntelliJ에서 재시작한 뒤 확인이 필요합니다.

## 참고: app.css
작업 중에 `app.css`가 20:12에 지워졌다가 20:19에 새 내용(21KB)으로 다시 생겼습니다. 이 세션에서 한 일은 아닙니다.

# 7부: 이 지역에서 다시 검색

## 사용 방법
1. 홈 지도를 **손으로 끌어서** 다른 동네로 옮깁니다.
2. 검색했던 곳에서 어느 정도 벗어나면(반경의 15%, 최소 300m) 지도 위쪽 가운데에 **"↻ 이 지역에서 다시 검색"** 버튼이 나타납니다.
3. 누르면 **지금 보이는 지도 가운데**를 기준으로 같은 반경에서 모임을 다시 찾습니다. 위쪽 문구는 "지도에서 고른 지역 기준 · 반경 5km"로 바뀝니다.

## 같이 넣은 것
- **검색 범위 표시**: 지금 목록이 어느 범위를 검색한 결과인지 지도에 옅은 노란 점선 원으로 보여 줍니다. 반경을 바꾸면 원 크기도 바뀝니다.
- 다른 지역을 검색한 뒤 **"내 위치로"** 버튼으로 돌아오면 이 버튼이 다시 나타나고, 누르면 "현재 위치 기준"으로 검색합니다.
- 목록에 마우스를 올려서 지도가 움직이는 경우처럼 사용자가 직접 옮기지 않았을 때는 버튼이 나타나지 않습니다.

## 확인 (8888 포트, 실제 카카오 지도)
- 지도를 실제로 1.6km 끌었더니 버튼이 나타났고, 누르니 결과가 5개에서 4개로 바뀌고 문구도 바뀌었습니다.
- 다른 지역 검색 → 내 위치로 → 버튼 → "현재 위치 기준" 흐름도 확인했습니다. 다만 마지막으로 고친 문구 부분은 8888이 아직 반영하지 않아서, 같은 코드를 브라우저에 넣어 확인했습니다.

# 8부: 날씨를 모르는 칸은 ❔로 표시

## 점(·)이 보이던 이유
| 경우 | 이유 | 이제 이렇게 보여요 |
|---|---|---|
| 이미 지난 시간 | 고를 수 없는 시간이에요 | 그대로 흐린 점(·) |
| 지금 이 시간 (예: 오후 8시) | 오후 8시에 발표한 예보는 **다음 시간(9시)부터** 나와요 | 9시 예보를 흐리게, 온도 앞에 **≈** |
| 4일 뒤 (3시간 간격) | 3시, 6시, 9시처럼 3시간마다만 예보가 있어요 | 사이 시간은 바로 옆 시간 예보를 흐리게, **≈** |
| 예보 범위 끝 (예: 11/23) | 자정 값 하나만 있고 나머지는 아직 없어요 | 0시는 그대로, 1시는 ≈, 2시부터 **❔ 예보 없음** |
| 그보다 먼 날 | 단기예보 범위 밖이에요 | 날짜 칸과 시간 칸 모두 **❔** |

- 예보가 몇 시간뿐인 날(11/23처럼 자정 하나)은 날짜 칸에 "1° 1°" 같은 숫자 대신 **❔ 일부만 예보**로 보여 줍니다. 숫자 하나로는 그날 날씨를 알 수 없기 때문입니다.
- 근처 시간 예보를 고르면 요약에 "약 1°"로 나옵니다. (안내 문구는 예보라서 필요 없다는 의견에 따라 뺐습니다)
- 기온 그래프는 실제 예보 값만 이어서 그립니다.

## 확인
8899 포트 임시 서버에서 실제 기상청 데이터로 오늘, 4일 뒤, 예보 범위 끝, 그보다 먼 날을 하나씩 눌러 위 표대로 나오는 것을 확인했습니다. 8888 포트에는 IntelliJ에서 **다시 빌드(Ctrl+F9)**나 재시작을 하면 반영됩니다.

# 10부: 모임 수정

## 사용 방법
1. 내가 만든 모임의 상세 화면에서 **모임 정보 수정**을 누릅니다. 모임이 시작되기 전에만 보입니다.
2. 만들기 화면이 그대로 열리고, 저장된 값이 채워져 있습니다.
   - 이름, 활동 종류, 설명, 정원, 장소가 채워져 있습니다.
   - 날씨 달력에는 원래 날짜·시간·분이 선택돼 있습니다.
   - 지도에는 원래 장소가 표시되고, 날씨도 그 장소 기준으로 나옵니다.
3. 고친 뒤 **수정 저장**을 누르면 상세 화면으로 돌아가고 "모임 정보를 수정했어요."가 나옵니다.

## 규칙
- **주최자만**, **모임 시작 전에만** 수정할 수 있습니다. 다른 사람이 주소를 직접 입력해도 "모임을 만든 사람만 할 수 있어요."가 나오며 막힙니다.

- 덤으로, 모임을 만들 때 입력 오류가 나도 **입력한 내용이 지워지지 않고 남습니다.**

# 11부: "기상청 예보" 문구, 오류 화면, Flyway

## 1. 문구 변경

- 날씨 달력에서 예보가 없을 때 나오는 안내도 "기상청 예보는 약 4일 뒤까지 나와요"로 맞췄습니다.

## 2. 오류 화면 정리
- 전에는 없는 모임 주소(예: `/gatherings/99999`)를 열면 영어로 된 500 오류 화면(Whitelabel)이 나왔습니다.
- 이제는 상황에 맞는 **한국어 오류 화면**이 나오고, "홈으로 가기"와 "이전 화면" 버튼이 있습니다.

| 상황 | 상태 코드 | 화면 문구 |
|---|---|---|
| 없는 모임·페이지 | 404 | 찾는 모임이나 페이지가 없어요 |
| 주소 형식이 잘못됨 (예: `/gatherings/abc`) | 400 | 요청을 처리할 수 없어요 |
| 권한 없음, 보안 확인 만료 | 403 | 이 요청은 처리할 수 없어요 (새로고침 안내) |
| 서버 오류 | 500 | 잠시 문제가 생겼어요 |

- 보안을 위해 오류의 자세한 내용은 화면에 보여 주지 않습니다.
- 지도 API(`/api/...`)는 지금처럼 JSON으로 오류를 돌려줍니다.
- 참고: 로그인이 필요한 영역의 모르는 주소는 로그인 전이면 로그인 화면으로 갑니다.

## 3. Flyway 도입 (DB 테이블 관리)
- **Flyway를 쉽게 말하면**: 테이블 구조를 SQL 파일로 기록해 두고, 앱이 뜰 때 아직 적용하지 않은 파일을 자동으로 실행해 주는 도구입니다. 오늘처럼 테이블을 손으로 고칠 필요가 없어집니다.
- `src/main/resources/db/migration/V1__init.sql`: 지금 로컬 MySQL의 실제 구조(gathering, participant, users)를 그대로 옮겨 적었습니다.
- **앞으로 테이블을 바꿀 때**는 이 파일을 고치지 않고 `V2__설명.sql` 같은 새 파일을 추가합니다.
- Hibernate는 이제 테이블을 직접 바꾸지 않고 **코드와 맞는지 확인만** 합니다(`ddl-auto: validate`). `application-local.yml`의 `update`도 `validate`로 바꿔 두었습니다.
- **로컬 DB(`nadeuri`)는 다음에 앱을 켤 때** Flyway가 "이미 V1"로 기록만 하고 V1은 실행하지 않습니다. 데이터는 그대로 유지되고, `flyway_schema_history`라는 기록용 테이블 하나만 생깁니다.
- 테스트(H2)는 지금처럼 Hibernate가 테이블을 만듭니다.

### 확인 방법 (로컬 MySQL에 임시 DB를 만들어 확인한 뒤 바로 지움)
| 경우 | 결과 |
|---|---|
| 새 DB | V1이 실행되어 테이블 3개가 생겼고, 앱이 정상으로 떴습니다 |
| 지금 구조를 복사한 DB (Flyway 도입 전 상태) | V1을 실행하지 않고 "기준점(V1)"으로만 기록됐고, 앱이 정상으로 떴습니다 |

두 경우 모두 "코드와 테이블이 맞는지 확인"을 통과했습니다. 임시 DB는 확인 후 지웠고, 실제 `nadeuri` DB는 건드리지 않았습니다.

## 4. 테스트
